**Версия:** 2.1.1 (versionCode 20), ветка `main`, коммит `9a0b01b`
**Дата:** 2026-11-11
**Объём:** 25 Gradle-модулей, 476 Kotlin-файлов, ~82 000 строк

**Как проверялось:** чтение исходников (пять параллельных проходов по подсистемам + точечная проверка каждой серьёзной находки). Сборка, тесты и запуск на устройстве **не** выполнялись. Номера строк актуальны для указанного коммита.

**Легенда**

- **P0** — потеря данных, безопасность, краш или ANR в типичном сценарии.

### P0 — исправлено

1. **1.1** Редактор больше не пишет `content://` на месте: SAF-документ не обрезается, результат сохраняется новым файлом в `files/books`, запись книги перепривязывается (`EditorViewModel.writeBack`).
2. **1.2** Восстановление бэкапа: файлы публикуются внутри транзакции и удаляются при её откате, операция в `NonCancellable`, конфликт строк по первичному ключу больше не отменяет весь restore (локальные данные выигрывают, счётчик `RestoreResult.skipped`), конфликт ревизии папки сохраняет локальную ревизию.
3. **1.3** Сеть вынесена из транзакции: `mergeAndWrite` и `mergeFolderMetadataAndWrite` фиксируют merge, затем пишут на сервер; база не сдвигается до успешной записи, повтор идёт обычным циклом.
4. **1.4** Доверие считается по `apkContentsSigners` (история ротаций — только для проверки апгрейда), `signatureHash` — полный набор подписантов.
5. **1.5** OAuth: одноразовый `state` генерируется и проверяется, redirect принимается только по точному `yomu://host`, у Shikimori PKCE S256, у MAL — plain, у AniList — `state` (PKCE в implicit-flow сервис не поддерживает).
6. **1.6** Cleartext выключен глобально (исключение — `localhost`/`.local` для домашних OPDS); WebDAV и индексы расширений требуют `https://` (loopback разрешён для локальных тестов).
7. **1.7** `datastore/` исключён из cloud-backup и device-transfer; PBKDF2 поднят до 600 000 итераций с версией формата (старые хэши проверяются), новый PIN — от 6 цифр, в экране блокировки есть задержка после неудачных попыток.
8. **1.8** Release без keystore больше не собирается; `assembleRelease` падает с объяснением, CI собирает `assembleFast`; апдейтер требует `SHA256SUMS.txt` и отказывается устанавливать APK без проверенного хэша; `mapping.txt` не публикуется.
9. **1.9** `EpubController.detach(view)` освобождает только свой WebView, `attach` закрывает предыдущий, хостинг переведён на `AndroidView(onRelease = …)`.
10. **1.10** Рендер PDF ограничен 6 Мпикс на страницу, для страниц без ночного режима используется `RGB_565`.
11. **1.11** `DONE` пишется условным `UPDATE … WHERE status='RUNNING'`; при отмене созданные файлы/запись книги удаляются.
12. **1.12** Отложенное удаление книг принадлежит ViewModel; при уничтожении VM без подтверждения удаление отменяется, при возврате на экран undo-снэкбар показывается снова.
13. **1.13** Ошибка записи `draft.json` показывается, флаг `dirty` остаётся в памяти; рабочая папка без читаемого флага считается черновиком.
14. **1.14** Лимит истории (150 МБ) применяется с первого шага; id резервируется атомарной записью индекса до изменения; битые шаги отбрасываются при загрузке.

## 1. P0 — критично

### 1.1 Сохранение из редактора может уничтожить оригинал

**Где:** `feature/editor/src/main/kotlin/app/yomu/feature/editor/EditorViewModel.kt:731-743`

**Что:** для книг с `content://` URI запись идёт через `contentResolver.openOutputStream(uri, "wt")` — сначала truncate, затем копирование. Ветка `file://` сделана правильно (`tmp` → `dest.new` → rename).

**Почему важно:** полный диск, отозванное разрешение SAF, ошибка OEM-провайдера или смерть процесса посреди копирования оставляют пользователя с обрезанным файлом — единственной копией книги.

**Как исправить:** писать в новый документ рядом (`DocumentsContract.createDocument`), затем `renameDocument`; либо запретить in-place сохранение для `content://` и предлагать «сохранить копией» (метод `saveAsNewBook` уже есть).

### 1.2 Восстановление бэкапа не атомарно

**Где:** `data/src/main/kotlin/app/yomu/data/backup/BackupManager.kt:183-197, 198-307, 267-280`

**Что:**
- файлы публикуются (`Files.createLink`) **до** `beginTransaction()` (:200); если транзакция падает, на диске остаются файлы без строк БД;
- вся операция не обёрнута в `NonCancellable`;
- любое расхождение по любой колонке (`sources.lastUsedAt`, `reading_sessions`, `collections.sortOrder`, `catalog_items.lastUpdateAt`) бросает `IOException` и отменяет **весь** restore (:279).

**Почему важно:** документированный путь восстановления («сделайте бэкап перед синхронизацией») не работает на устройстве, где приложение уже успело обновить служебные поля. Плюс возможна «полувосстановленная» библиотека с файлами-сиротами.

**Как исправить:** журнал намерения + откат опубликованных файлов при провале транзакции; `withContext(NonCancellable)`; merge по строкам с описанным приоритетом и отчётом о пропущенных записях вместо abort.

### 1.3 Сеть внутри транзакции БД

**Где:** `data/.../backup/SyncWrite.kt:20-24`, `data/.../backup/FolderMetadataSync.kt:25-51`

**Что:** `db.withTransaction { SyncMerger.merge(); backend.write() }` — HTTP/WebDAV-запрос выполняется, пока открыта единственная writer-транзакция SQLite. В папочном синке внутри транзакции ещё и хэшируются все страницы всех папок.

**Почему важно:** блокируются запись прогресса чтения, загрузки, отметок глав — вплоть до ANR и `SQLiteDatabaseLockedException`; при отмене локальный merge откатывается уже после того, как сервер принял состояние (`SyncManager` повторяет цикл до 3 раз).

**Как исправить:** outbox-таблица — транзакционно фиксировать намерение и локальный merge, публиковать вне транзакции, а при конфликте разрешать через существующий путь повторного merge.

### 1.4 Доверие подписям расширений

**Где:** `data/.../source/ExtensionManager.kt:624-631`, `:231`, `:69`

**Что:** `signaturesOf()` возвращает `signingCertificateHistory` (историю ротаций), а `isTrusted()` принимает «любой из» сертификатов. `signatureHash` пиннит `signatures.lastOrNull()`, то есть не обязательно текущий подписант.

**Почему важно:** APK, подписанный отозванным или скомпрометированным ключом, продолжает считаться доверенным для пакета и исполняется в процессе приложения.

**Как исправить:** для решения о доверии использовать `signingInfo.apkContentsSigners` и сравнивать полный набор подписантов; историю использовать только для проверки легитимности апгрейда.

### 1.5 OAuth-редирект без защиты

**Где:** `app/src/main/AndroidManifest.xml:67-82`, `data/.../tracking/TrackerManager.kt:60`, `data/.../tracking/AniListTracker.kt:30-39`, `ShikimoriTracker.kt:41-47`

**Что:** `TrackLoginActivity` экспортирована и слушает кастомную схему `yomu://…-auth`; содержимое URI принимается по префиксу, `state` не передаётся и не проверяется, PKCE отсутствует. У AniList токен приходит во фрагменте URL.

**Почему важно:** кастомная схема не верифицируется. Любое приложение может перехватить редирект (для AniList — сам access token) или, наоборот, запустить Yomu с поддельным `yomu://anilist-auth#access_token=…` и молча залогинить пользователя в чужой аккаунт.

**Как исправить:** случайный `state` в `TrackerStore` + обязательная проверка «логин действительно начинался», PKCE для всех сервисов, предпочтительно `https://` App Link с `assetlinks.json` или Custom Tabs с возвратом через `onResume`.

### 1.6 Cleartext разрешён глобально

**Где:** `app/src/main/res/xml/network_security_config.xml:5`, `data/.../backup/SyncBackends.kt:217-227`, `app/.../AppModule.kt:333`

**Что:** `base-config cleartextTrafficPermitted="true"` для всех хостов. При этом WebDAV принимает `http://` и отправляет `Authorization: Basic …`, а ссылка `tachiyomi://add-repo`/`mihon://extension-store` принимает `http://`-репозиторий, ключ доверия берётся из скачанного индекса.

**Почему важно:** на враждебном Wi-Fi читаются и подменяются токены трекеров, пароль WebDAV, содержимое синка (позиции, заметки, файлы книг). Для репозитория расширений это прямой путь к исполнению чужого кода (MITM → свой индекс → свой ключ → свой APK).

**Как исправить:** `false` в `base-config`; `domain-config` с cleartext только для явно добавленных пользователем OPDS-хостов; https-only для WebDAV и репозиториев расширений; показывать отпечаток ключа при добавлении стора.

### 1.7 Секреты уходят в облачный бэкап

**Где:** `app/src/main/res/xml/data_extraction_rules.xml:4-7`, `core/datastore/.../AppSettings.kt:268, 300`

**Что:** в `cloud-backup` и `device-transfer` включён `file/datastore/` — файл, где лежат `pin_hash`, `webdav_password`, `github_token`, `deepl_key`, `libre_key`, `llm_key`. Собственный экспорт приложения эти ключи исключает (`privateKeys`).

**Почему важно:** секреты уезжают в облако Google вопреки модели приватности приложения; после восстановления на новом устройстве возвращается `app_lock=true` с хэшем PIN, который пользователь может не помнить. PIN дополнительно слаб: PBKDF2-HMAC-SHA256, 20 000 итераций, 4–12 цифр, без счётчика попыток (`feature/settings/.../SettingsExtras.kt:373`).

**Как исправить:** исключить `datastore/` из `cloud-backup` (или вынести секреты в `noBackupFilesDir`/Keystore), поднять итерации до актуальных рекомендаций OWASP, ввести счётчик попыток и экспоненциальную задержку.

### 1.8 Release может быть подписан публичным debug-ключом

**Где:** `app/build.gradle.kts:67`, `feature/settings/.../Updates.kt:375, 448, 490-494`

**Что:** при отсутствии `YOMU_KEYSTORE_PATH` release подписывается `debug`-конфигом (ключ `gradle/debug.keystore`, пароль `android`, лежит в репозитории). Апдейтер принимает APK, если его подписант совпадает с установленным, а при отсутствии `SHA256SUMS.txt` вообще не проверяет хэш.

**Почему важно:** для debug-подписанного релиза ключ публичен — любой может собрать вредоносный `app.yomu.reader`, который (а) установится поверх опубликованного и (б) пройдёт собственную проверку обновлений приложения.

**Как исправить:** валить `assembleRelease` без keystore (fallback оставить только для `fast`), не публиковать debug-подписанные APK, требовать подписанный файл контрольных сумм (minisign/GPG с зашитым в приложение ключом) и отказываться от установки без него.

### 1.9 `EpubController.detach()` уничтожает не тот WebView

**Где:** `feature/reader-epub/.../EpubController.kt:163-170`, `feature/reader-epub/.../EpubReaderView.kt:19`

**Что:** `detach()` не принимает view и уничтожает текущий `webView`; вызывается из `onDispose`. Если Activity пересоздаётся при живом `EpubController` (смена системного размера шрифта, локали, «не хранить активности»), новая композиция успевает вызвать `attach(newView)`, после чего старая вызывает `detach()` — и уничтожает **новый** WebView.

**Почему важно:** все `js()` становятся молчаливыми no-op, `eval()` возвращает `null`, книга показывает пустую/застывшую страницу без ошибки. Поворот экрана не страдает только потому, что `orientation|screenSize|…` перечислены в `configChanges`.

**Как исправить:** `detach(view: EpubWebView) { if (webView === view) … }`, в `attach()` освобождать предыдущий, а хостинг перевести на `AndroidView(onRelease = …)` — как уже сделано в `DocxLayoutScreen`.

### 1.10 PDF: нет лимита на пиксели страницы

**Где:** `feature/reader-pdf/.../PdfController.kt:74-82`, `data/.../book/Pdf.kt:62-79`

**Что:** ширина страницы = `widthPx * renderScale` (×2 в постраничном режиме, ×1.5 в развороте), высота выводится из пропорции; ограничение только по ширине (4096). `beyondViewportPageCount = 1`, кэш — `maxMemory/6`.

**Почему важно:** QHD-телефон + A4 даёт ≈2880×4073 ARGB ≈ 47 МБ на страницу, а высокие страницы (например, печать в PDF) — единичные аллокации >150 МБ. Это реалистичный `OutOfMemoryError` на средних устройствах.

**Как исправить:** ограничивать по площади (`w*h ≤ 4–6 Мпикс`), использовать `RGB_565` для страниц без ночного режима, считать масштаб от требуемого размера на экране, а не фиксированным множителем.

### 1.11 Отменённая загрузка «оживает»

**Где:** `data/.../download/DownloadRepository.kt:507, 601`

**Что:** после цикла записи байтов/страниц состояние `DONE` пишется безусловно (`dao.get(t.id)?.let { dao.update(it.copy(status = DONE, …)) }`), без проверки, что задача всё ещё `RUNNING`. `cancel()`/`clearQueue()` при этом выставляют `CANCELLED` и удаляют `.part`.

**Почему важно:** отмена между последней проверкой `stillRunning` и терминальной записью всё равно импортирует файл в библиотеку, помечает главу скачанной и возвращает строку в `DONE`.

**Как исправить:** условный `UPDATE … WHERE id=:id AND status='RUNNING'`; если строк не изменено — удалить только что созданный файл.

### 1.12 Удаление книги может пройти без undo

**Где:** `feature/library/.../LibraryScreen.kt:258-264`, `feature/library/.../LibraryViewModel.kt:456-474`

**Что:** удаление «прячется» сразу (`pendingDelete`), а коммит привязан к snackbar в scope экрана. Уход с таба/экрана отменяет корутину; `onCleared()` доделывает удаление через `GlobalScope`.

**Почему важно:** книга исчезает, «Отменить» не показывается, а удаление всё равно происходит позже — молча и необратимо.

**Как исправить:** владение отложенным удалением перенести в ViewModel (job/таймер), а не в композицию; при уничтожении VM без явного коммита — отменять удаление, а не выполнять.

### 1.13 Черновик редактора можно потерять молча

**Где:** `feature/editor/.../EditorViewModel.kt:240-244, 161-179`

**Что:** `setDirty()` глотает ошибки записи `draft.json`, а именно этот флаг защищает рабочую папку от `deleteRecursively()` при следующем `start()`. Порча/отсутствие файла трактуется как «черновика нет».

**Почему важно:** один неудачный write (полный диск, пропавший `filesDir`) — и при следующем открытии книги удаляются несохранённые правки и вся история.

**Как исправить:** ошибку записи показывать и держать `dirty` в памяти; существующую рабочую папку без читаемого флага считать черновиком (`DraftFound`), а не мусором.

### 1.14 История редактора может занять гигабайты

**Где:** `feature/editor/.../History.kt:106-110`, `EditorViewModel.kt:369-437`

**Что:** лимит `MAX_BYTES` (400 МБ) применяется только когда шагов уже больше `MIN_STEPS = 50`. Операции «на весь документ» (`cleanStyles`, `fix`, `replaceAll`, `translateChapters`) снимают снапшот всех файлов.

**Почему важно:** 50 шагов × 100 МБ EPUB ≈ 5 ГБ в `files/editor/<bookId>/history` до первой обрезки; на полном диске перестают проходить любые изменения.

**Как исправить:** применять лимит с первого шага, ввести режим «не хранить снапшот» для массовых операций и сжимать текстовые снапшоты (EPUB-текст жмётся примерно в 10 раз).

## 3. Архитектура и качество кода

- **Слой `domain` обойдён.** 43 файла в `feature/*` импортируют `app.yomu.data.*` или `app.yomu.core.database.*` напрямую; ViewModel-и выполняют роль use case-ов. Это ускоряет разработку, но мешает тестируемости и скрывает зависимости.
- **Монолиты:** `ReaderViewModel.kt` — 1578 строк, `DocxLayout.kt` — 1238, `EpubWorkspace.kt` — 1065, `data` — 27 241 строка в 173 файлах. `feature:reader` зависит от всех движков сразу.
- **`GlobalScope`** в `ReaderViewModel` (3 места) и `LibraryViewModel`; **`runBlocking`** в `EpubController.serve`, `Metadata`, `DictionaryRepository`, `Workers`.
- **`configChanges` на Activity** маскирует lifecycle-баги: часть проблем (в том числе WebView из 1.9) проявляется только при пересоздании, а не при повороте.
- **Нет `SavedStateHandle`** для поисковых запросов и фильтров каталога — смерть процесса всё теряет, хотя сами фильтры-настройки хранятся в DataStore.
- **Тестовый разрыв.** Покрыты парсеры, редактор, SM-2, лемматизация, экспорт; не покрыты: возобновление загрузки по HTTP Range, сценарии «сохранить слово», «добавить закладку», «скачать главу», открытие PDF/CBZ. Цель 60 % не достигнута (признано в `KNOWN_LIMITATIONS`).

## 4. Найдено при ручной проверке

### 4.1 Нельзя отключить регулировку яркости свайпом

**Симптом.** Свайп у левого края меняет яркость; выключить именно это, оставив тёплый фильтр, нельзя.

**Причина в коде.** В настройках есть **один** переключатель на оба края:

- `domain/.../model/ReaderSettings.kt:136` — `val edgeGestures: Boolean = true`;
- `feature/reader/.../ReaderSettingsSheet.kt:473` — `PreferenceSwitch(rs_edge_gestures, c.edgeGestures, …)`;
- `feature/reader/.../ReaderScreen.kt:427-442` — `enabled = common.edgeGestures && …` для всего блока:
  `EdgeGestures.kt:60-64`: левая полоса — яркость, правая — тёплый фильтр.

Отдельного поля/переключателя для яркости нет; гранулярность — «оба края или ничего». Дополнительно жест слушает `PointerEventPass.Initial` (`EdgeGestures.kt:56-82`), поэтому даже включённый свайп конфликтует с вертикальным скроллом и системным back-жестом у края — это усиливает ощущение, что настройка «не отключается».

**Что сделать.**
1. Заменить `edgeGestures: Boolean` на набор/режим: `EdgeGesturesMode { OFF, BRIGHTNESS, WARM, BOTH }` либо два независимых флага `edgeBrightness` / `edgeWarm`.
2. Вынести в глобальные настройки ридера **и** в per-book настройки, добавить в поиск по настройкам.
3. Слушать жест на `Main`/`Final`, сузить полосу (сейчас 12 %), не потреблять событие, если контент уже обработал скролл.
4. Подсказку `ReaderTapZonesHint` строить по фактически включённым краям, а не по общему флагу.

### 4.2 Вход в YouTube не работает

**Симптом.** Попытка «войти»/открыть видео, требующее аккаунта, ни к чему не приводит.

**Причина в коде.** Входа нет вовсе:
- `data/.../audio/YouTubeClient.kt:75-229` — InnerTube-клиент с анонимными `ANDROID_VR`/`IOS`/`WEB`; ни OAuth, ни cookie-jar для `youtube.com`, ни веб-логина через WebView;
- `:215-217` — `status == "LOGIN_REQUIRED"` превращается в `YouTubeException.Reason.BLOCKED`;
- `data/.../audio/AudiobookStore.kt:230-231` — наружу это `AppError.AudioLink(YOUTUBE_BLOCKED)`;
- в `feature/audio` нет ни экрана аккаунта, ни настроек YouTube (ресурсы `common_signin_button_*` в build-каталоге — из `play-services`, а не из кода приложения).

То есть «вход не работает» — это отсутствующая функция, а не сломанная.

**Что сделать (по возрастанию сложности).**
1. Честный UI: для `BLOCKED`/`LOGIN_REQUIRED` показывать «YouTube требует вход или видео недоступно» + кнопки «Открыть в браузере» и «Повторить», а не общую ошибку.
2. Поддержать `visitorData`/PO-token и обновлять список клиентов (`YouTubeClient.kt:317-330`) — это временно снижает частоту блокировок, но не даёт аккаунт.
3. Полноценный вход: WebView на `accounts.google.com` с последующим переносом cookie (`SAPISID`, `__Secure-3PSID`) в клиент. Хрупко, требует хранения секретов в Keystore и явного предупреждения, зато даёт приватные плейлисты, age-restricted и «members-only».
4. Альтернатива без аккаунта: импорт ссылок/плейлистов и проигрывание локальных файлов; официальный YouTube Data API для метаданных (без потоков).

**Риск:** любые варианты 2–3 нарушают условия YouTube и ломаются при изменении InnerTube — это нужно явно написать в `KNOWN_LIMITATIONS` и не обещать в UI «вход работает всегда».

### 4.3 YouTube-аудиокниги не работают

**Симптом.** Добавленная YouTube-книга/плейлист не играет (или не скачивается).

**Причина в коде.**
- `YouTubeClient.kt:200-229` перебирает клиентов и бросает `BLOCKED`, если ни один не отдал поток: типично для VPN/дата-центровых адресов и после серии запросов («bot check»); часто остаётся только iOS-клиент с HLS;
- `KNOWN_LIMITATIONS.md` фиксирует: age-restricted, members-only, «made for kids» не играют; HLS-only нельзя скачать в офлайн (нужен одиночный файл);
- ссылки на поток живут несколько часов — за ночь пауза превращается в новый resolve, а без сети это ошибка;
- при первом же `BLOCKED` книга добавляется, но остаётся нерабочей — нет ни пометки, ни объяснения в библиотеке.

**Что сделать.**
1. Диагностика в UI: показывать точную причину (`BLOCKED`/`UNPLAYABLE`/`NOT_FOUND`), кнопку «Проверить ссылку» и «Открыть на YouTube».
2. Кэшировать успешный resolve и обновлять его заранее (за 30–60 минут до истечения), а не по факту ошибки.
3. Для скачивания: если доступен только HLS — писать HLS-сегменты в офлайн-кэш (или честно отключать кнопку «Скачать» с пояснением).
4. Не создавать «мёртвую» книгу: добавлять в библиотеку только после успешного resolve, иначе — тост с причиной.
5. Обновляемость: вынести список клиентов и параметры в конфиг, добавить тест `YouTubeLiveTest` в ночной CI, а не только локально.

- Экспорт/импорт настроек исключает секреты (`AppSettings.privateKeys`).

- Сборка и тесты не запускались: выводы сделаны по коду, а не по воспроизведению.
