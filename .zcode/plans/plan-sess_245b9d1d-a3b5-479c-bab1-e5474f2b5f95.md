# Этап 1: завершение синхронизации книг и данных

## Контекст

Разведка кода показала, что синхронизация устроена надёжнее, чем следует из плана: 4 документа с CAS (WebDAV — сильные ETag, SAF — staging+verify), проверка SHA-256 при передачах, трёхстороннее слияние аннотаций с доказательствами версий, томбстоуны записей, ~30 тестовых наборов. Критерий плана «не потерять данные незаметно» уже соблюдён архитектурно — за счёт того, что синхронизация *останавливается* при неоднозначности.

Остались ровно четыре незавершённых узла, и два из них существуют как готовые, но неподключённые примитивы:
1. **Изменённые файлы обычных книг** — сейчас любой правленный файл (включая PDF, куда приложение само записало выделения) останавливает всю синхронизацию с текстовой ошибкой (`BookFileSync.kt:93`).
2. **Legacy-папки** — `FolderIdentityMigration.kt` написан, но без вызывающего кода; одна старая папка блокирует перенос файлов целиком (`FolderSyncCoordinator.kt:18`).
3. **Изменения страниц папок** — добавление работает, изменение/удаление страницы → `CHANGED_PAGE`/`MISSING_PAGE`, только текст ошибки.
4. **Удаления книг между устройствами** — `BookDeletionGuard`/`SharedBookRevision`/`LocalBookRevision` готовы и протестированы, но «deliberately not wired».
5. **Интерфейс разрешения конфликтов отсутствует** — все конфликты превращаются в одну строку `lastSyncError` в настройках.

Этапы 2–3 (трекинг, форматы) делаются следующими заходами после завершения Этапа 1; проверка на устройствах — за вами, я подготовлю чек-лист.

## Ключевые решения (можно отклонить при утверждении)

1. **Изменённый файл** — не идентификация по хешу файла, а переход книги на стабильный идентификатор `book:<uuid>` (как у папок) по явному действию пользователя «Принять новую версию»: загрузка нового блоба, перепривязка записей синхронизации (прогресс/выделения/заметки/закладки остаются на книге), журналируемая транзакция. Повторные изменения после принятия — простая новая версия блоба. Конфликт, если файл изменён и локально, и на другом устройстве.
2. **Самоизменённые PDF** (запись выделений приложением) — принимаются автоматически: `PdfAnnotationStore` даёт проверить, что изменение сделано нашим воркером, а не извне.
3. **Удаления книг** — повторно используется существующая настройка `syncDeletions`; маркер удаления публикуется устройством, где книга удалена и была в базе слияния; принимающее устройство удаляет книгу **только если она не менялась** с последней синхронизации, иначе конфликт с сохранением данных. Правило для удалённых копий файлов: блобы на сервере не удаляются (документируется; индексная запись удаляется, маркеры устаревают за 180 дней).
4. **Старые клиенты** — как и для метаданных v3: устройства одной цели синхронизации должны быть обновлены; это остаётся задокументированным ограничением.

## Подэтапы (каждый — сборка + тесты перед следующим)

**0. Точка сохранения.** Каталог не git-репозиторий: `git init` + начальный коммит, далее коммит после каждого подэтапа.

**1.1. Структурированные проблемы + экран конфликтов (фундамент).**
- Общий тип проблемы синхронизации поверх существующих `AnnotationSyncProblem`/`FolderSyncProblem` (+ новые виды: изменённый файл, конфликт удаления, коллизия папок). Список проблем последней синхронизации сохраняется в `filesDir/sync/problems.json`, а не только строка `lastSyncError`.
- В `feature/settings`: строка ошибки становится кнопкой → экран «Конфликты синхронизации» (список: книга/папка, причина, действие). Действия добавляются в последующих подэтапах.
- Файлы: `SyncManager.kt` (сбор проблем вместо первого исключения), `feature/settings/.../SettingsV2.kt` + новый экран, strings.xml (RU+EN).

**1.2. Изменённые файлы обычных книг.**
- `BookFileSync`: расхождение содержимого → структурированная проблема «файл изменён» и пропуск файловой части этой книги (метаданные продолжают синхронизироваться), вместо остановки всего.
- Механизм принятия версии: общий с миграцией папок перепривязывающий движок (ключи `SyncState`, `SyncBase`, доказательства версий аннотаций, `TrackLink.owner`, `books.json`, `folder_sync_bases`) + долговременный журнал миграции (`filesDir/sync/`) для доката после сбоя; переиспользуются `FolderIdentityMigration`-паттерн, `AtomicFile`, `SyncJson`.
- Варианты в UI: «Принять мою версию» / «Загрузить версию другого устройства» (замена файла, bookId сохраняется). Автопринятие для самоизменённых PDF.
- Тесты: принятие при одном изменении, конфликт при обоюдном, обрыв после каждого шага (журнал), старый клиент — fail-closed.

**1.3. Миграция legacy-папок на стабильные идентификаторы.**
- Подключить `FolderIdentityMigration`: действие из экрана конфликтов при проблеме LEGACY. Журнал хранит old→new и пересчитанные доказательства версий (комментарий в коде требует «journal that can safely reconstruct them»).
- Координированная перезапись: yomu-sync.json (v3 + folderRevisions), folders.json, books.json, tracking.json, все базы целей (`base.json`, `sync-books/*`, `sync-tracking/*`, строки `folder_sync_bases`), строка книги в Room — под мьютексом синхронизации, с CAS и журналом; сбой → докат или fail-closed с понятным сообщением.
- Сохранность порядка страниц, прогресса, аннотаций, привязок трекеров; тесты на двух «библиотеках», обрыв и конфликт обоих идентификаторов.

**1.4. Изменения страниц папок (добавление/изменение/удаление).**
- Локальное изменение страниц → управляемая публикация новой версии манифеста: `FolderPositions`/`FolderPositionMap` с политикой разрешения (позиции, указывающие на изменённые/удалённые страницы, сбрасываются с видимым отчётом, а не `CHANGED_PAGE`-остановкой), подтверждение из экрана конфликтов.
- Принятие изменённой версии с другого устройства: «Принять удалённую версию» — коммит с ремапом позиций и отчётом о сброшенных привязках; «Оставить мою» — публикация своей. Совпадение при повторном импорте (SIMILAR): «Привязать к общей копии» (перепривязка идентификатора тем же движком) или «Оставить обе».
- Файлы: `FolderSyncCoordinator.kt`, `FolderMerge`, `FolderPositionMap.kt`, `FolderRevisionCommit`, конфликтный экран.

**1.5. Передача удалений книг (подключить `BookDeletionGuard`).**
- База слияния файлов получает версии книг (`SharedRevision` по `SharedBookRevision.capture`); устройство, у которого книга была и исчезла, публикует маркер (guard.propose) только при неизменном удалённом состоянии.
- Приём: guard.receive в транзакции — удаление строки книги и файла только при совпадении всех отпечатков; при изменении — конфликт, данные сохраняются; книга с удалением томбстоунит свои записи синхронизации, чтобы они не воскресли.
- Обновить `set_sync_deletions_sum` (теперь книги тоже), правило копий файлов — в документацию. Восстановление из бэкапа (clearBase) после маркера → конфликт → данные сохраняются (проверить тестом).
- Тесты на `BookDeletionGuardTest`-базе: publish/apply/conflict, отложенное устройство >180 дней, restore-потом-sync.

**1.6. Сведение и документация.**
- Проверить сценарии: восстановление бэкапа → синхронизация; повторный импорт после удаления (suppressed очищается — уже есть тест, добавить для маркеров); обрыв передачи → безопасный повтор.

Реальные серверы и устройства из этой среды недоступны — это остаётся на вас и фиксируется как не проверено.

## Явные ограничения результата (не выдавать за исправленное)

- Общая папка не защищает от одновременной записи (документируется, уже есть).
- Прогресс онлайн-глав по-прежнему last-writer-wins по `updatedAt`.
- Блобы на сервере не удаляются автоматически.
- Старые клиенты в общей цели синхронизации не поддерживают принятые версии и маркеры удаления — обновление всех устройств обязательно.
- Реальные устройства/WebDAV не проверены; две библиотеки корректно обмениваются данными пока только в симулированных тестах.
